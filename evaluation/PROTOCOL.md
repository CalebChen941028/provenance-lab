# ProvenanceLab 评测协议（Evaluation Protocol）

> 口号说 every claim stands scrutiny——评测体系自己也要经得起推敲。本协议定义 L0（遥测基线）与 L1（植错测试集）两层评测。

## L0 · 内建遥测（每次全流程运行自动产生）

- 每次运行自动落盘 `<产物目录>/99-metrics.json`，并在最终返回的 `metrics` 字段携带同一数据
- 指标：证据纳入数、引文核查关卡（抽查数/通过/失败/修正保留/剔除/待确认 pending/未绑定意见）、统计审稿（原始与实际判定/轮数/未关闭 major/未关闭摘要错误 openSummaryIssues/待关闭 minor）、同行评审（轮数/遗留 major/待关闭 minor）、答辩拷问（问数/未答出）、引文深审（引用点数/问题数/覆盖异常/显式删除点/题录未确认 bibliographyUnknown/仅摘要级/无原文）、文献归档（已下载/待获取）、复现性（含 reproFailed）、findings/notCovered 总数、模式与档位；`deterministic` 段记录确定性工具层（工具调用与失败数、检索源失败数、去重前后候选数、证据表标识符解析尝试/未确认 unresolved/不存在/撤稿数、白名单终检、statcheck、analysisManifest 的 listed/verified/ok（仅当前清单快照，非独立重跑）以及 sourceIntegrity 的 available/unchanged/changed 与 issues（仅跟踪执行材料的版本变化，不证明独立重跑）结果）
- 用法：跨运行汇总成基线表。固定材料且核验口径一致时，质量不得退化；文献纳入数、问题检出数与下载数只描述规模，不能直接当作越高越好的质量分数。不同运行的证据内容或SAP不同，须披露比较边界，不能由计数升降推断能力变化。

## L1 · 引文深审植错测试集（`citation-error-cases/`）

**测什么**：引文深审关卡（citation-audit 模式）对已知问题引用的检出率与对干净引用的误报率。

**怎么跑**：

1. **ground truth 核验**：v0.2 全部案例已于 2026-10-24 经 PubMed / Crossref / OpenAlex 逐条核验（`verified_by` 字段记录依据）。v0.1 由作者记忆构建，核验发现 S4、S8 的 DOI 指向无关论文、PMID 35149136 被误标为横断面研究（实为 meta 分析）、S10 陈述与原文主题不符，且参考文献条目附带了泄露答案的提示语——v0.1 的任何得分均不可用。今后新增案例必须先过 API 核验再入集
2. 运行：`/provenance-lab` → 模式选 `citation-audit` → `draftPath` 指向 `citation-error-cases/seeded-draft.md`（跨 harness：按 core 协议对 seeded-draft 执行 S7.5 流程）
3. 评分：citation-audit 模式会写出结构化明细 `05a-citation-audit.json`，用 `python3 evaluation/score_l1.py <run1>/05a-citation-audit.json <run2>/… <run3>/…` 确定性计分（多文件时报均值与范围，并单独报告确定性层对 S1–S4、S10 的判定）。规则如下：
   - **问题案例**（S1–S9）判"通过" = 该条被标为问题（任一维度不达标），且 expected 给出的具体维度判定一致
   - **非问题案例**（S10 更正状态文献、S11 干净对照）判"通过" = 未被判为问题；S10 还须标注 retractionStatus=corrected
   - 兼容D44：bibliography=mismatch也计为问题，干净/更正对照被误报题录错误须扣特异度；旧记录缺字段按unknown显示，不改原四维分数或S1–S9的具体维度要求。
   - 汇总：敏感度 = 检出问题数/9；特异度 = 非问题案例未误报数/2；附各案例文本层级（textLevel：全文/仅摘要级/无原文）

**节奏**：任何对引文深审/文献状态审计人设或流程的修改后必须重跑；LLM 非确定性——正式记录报 **3 次运行的均值±范围**。结果汇总表提交至 `evaluation/results/`（单次原始产物加入 .gitignore 不提交）。

## 局限与后续（如实声明）

- L1 只覆盖引文维度；统计忠实度与交叉校验的植错集属 L2（roadmap）
- 用 LLM 评 LLM 存在循环性——关键版本建议人工专家复核抽样
- 检出率是关卡能力下限估计，不代表全流程正确性上界

## 迭代回归测试规范（轻量课题加速，开发循环专用）

优化迭代的重试验证**不跑重型课题**——用轻量课题做回归，收敛后如有需要再做一次全尺度确认。

### 分层验收（2026-10-28用户授权采用）

从本次D45重判起，开发验收分别报告下列结论，不再以终检的一个`issues`状态代替全部裁决。此次为事后更正验收口径，保留旧结论和原始产物；下一轮启动前固定本节判据。工作流原`passed/issues`仍保留为交付待办信号，本次不修改执行逻辑或任何科研关卡。

| 层次 | 通过所需证据 | 阻断项与允许边界 |
|---|---|---|
| 工程运行 | 规定预检通过；真实运行能交付完整产物、正确传递文件与参数、保留复核账本、生成可追溯指标 | 未处理异常、丢失参数/结果、发布失败、确定性误报引发错误处置、需人工修改脚本才完成，均不通过。网络限流正确降级并披露不单独阻断。离线或脚本化通过只能判预检通过，不能替代真实运行 |
| 科研完整性 | 引文身份及状态、修正保留/剔除链、SAP时间顺序、code-to-data、统计结论与分析版本逐项有证据；分析清单和独立重跑分别核验 | 编造或错引仍获引用、撤稿/关注条目违规放行、未经修正删除可纠正证据、结果驱动改SAP、原始数据越界、虚假核验声明、影响结论的计算错误均阻断。状态未知、覆盖不足或缺少核查证据须判待验证并限制相应论断，不能当通过，也不直接推定造假 |
| 论文交付质量 | 区分演示材料已交付、需修订、达到目标用途；声称可投稿须核实与投稿相关的问题已关闭 | 模拟数据声明、付费墙、真实数据缺失、测量或因果边界、答辩待补可作为已披露限制；若本轮用途不要求解决，不单独否决工程运行。minor按实际影响判定，不能因标签为minor放过数字/引文错误，也不因措辞建议未关闭否决整个软件 |

每层只用“通过／未通过／待验证”，论文另标用途与交付状态；已验证子项与剩余项同时列出。不存在由层间平均分抵消完整性阻断项的总分。只有本轮用途所需各层均通过，才能称该用途整体验收通过；不得把开发部署称为模型能力认证或投稿许可。

验收发现须分为已确认错误、已确认误报、未核实意见、已披露范围限制，记录证据及对应层。`findings`/`notCovered`的字符串数不等于缺陷数；聚合项须展开，重复事项不重复计缺陷。已关闭项不再阻断，未验证的新修复不能追溯改写旧运行的成功状态。

引文能力继续按L1真实三次运行报逐例结果、均值与范围，沿用现有真值和计分，不以mock代替。尚无实测基线时不临时设置或改动能力分数线；未完成L1只能写能力待验证。后续能力阈值须在新试跑前记录依据并冻结。本轮修复优先用保存的失败材料及干净对照验证，再跑真实关卡；需要确认全流程稳定时，以固定版本、参数、材料/种子口径的连续两次无工程阻断运行判断，不要求开放研究中永无改进建议。

性能单列报告。30–60分钟/<8M tokens保留为历史预期，不作当前质量验收门槛；只有在输入范围与质量可比时，才评估目标环节的成本变化。D30已按D29的降幅阈值宣布当时token优化收敛；后来修复正确性缺陷属于另一项工作，不能据此反称同一优化始终未收敛。

**验收判据**（与优化合入条件一致）：

7. 版本与覆盖边界：初次分析及 verifyCommand/可移植性修复后、统计审稿前记录源码基线，归档结束、审计包前比较分析/SAP脚本与锁文件。增删改使此前复现记录不能确认最终版本；不得以未变或清单匹配冒充独立重跑。第二轮除确定性硬失败外的所有失败（含同标识符新问题）须获最后定向修正复核。图表返工后独立复核一次，仍不过就披露；审计包/总结明确全文、摘要、无原文计数，不以“全部通过”覆盖文本不可得。 D42末轮须按G键区分 originalIssues 与 newIssues，新问题或无效返回留pending并禁引。验收02与evidence-final.json的状态一致性，核对组合引用的初审身份绑定；none不能作为新增白名单来源。分析输出目录不得被发布入口文件替代；已见主种子结果的设计顺序须披露。

**离线预检（零 token，每次改动先过）**：`python3 -m unittest discover -s tools/tests`（工具层）、`python3 -m unittest discover -s evaluation/tests`（续跑画像与评分兼容）、`node ci/typecheck.mjs`（工作流类型）、`node ci/mock-run.mjs`、`--no-stats` 与 `--no-tools`（脚本化 agent + 真实工具的对抗式端到端运行：核查员漏判、检索源崩溃、白名单外引用、p 值不自洽都必须被代码关卡拦下；工具缺失时每个关卡必须回落）、`python3 ci/check_sync.py`（协议副本逐字节一致、中英协议关键锚点齐全）。离线预检不过，不进轻量回归。`--no-stats` 验证零匹配不能判通过；`--no-tools --stale-recheck` 验证范围外失败id不能计修正通过；带工具的 mock 与在线单元测试仍需联网，但不消耗 LLM token。`--no-tools --audit-recheck-errors` 验证缺失/重复/范围外深审键不能抹除原问题，`--no-tools --audit-remove` 验证明示删除须保留原判定与依据。S2 的可纠正警示即使漏填 failedIds 也须修正复核，不能静默遗漏。 D41追加`--no-tools --gate-same-id-error`（同文献新错误）、`--no-tools --gate-drop-entry`（修正时未获准删换ID）、`--verify-after-portability`（核验修好后的版本）、`--source-drift`（清单仍匹配而源码变化须使旧复现失效）与`--no-tools --visual-recheck-pass`（返工后独立再查，按最终结论落状态）。

**不可优化的固定项（integrity invariants）**：借鉴 Harness²（google-research/harness2，Apache-2.0）把 harness 改动分为"执行机制"与"领域知识"两个维度的做法，本项目再划出第三类——**任何优化都不得触碰的科研完整性规则**：引用白名单、撤稿/关注硬关卡、SAP 先于结果冻结、code-to-data、付费墙与反爬不绕过、未覆盖清单如实披露、工具结论优先于 agent 自报。优化只能改执行机制（工具指引、token 预算、编排顺序、成文纪律）；一项改动若需要放松上述任一规则才能见效，判为不合入。

**对照试跑**：引文深审、状态审计相关人设改动，用 L1（有 ground truth）对新旧两版各跑一次再决定合入；Harness² 在无 ground truth 时用执行行为对比合成改进，本项目有植错集，应优先用 ground truth 对比。

**循环**：离线预检 → 修复并用固定失败材料/干净对照验证 → 必需的真实关卡验证 → 按分层判据记录 → 用户授权后提交部署（涉及执行协议仍全域同步D23）。开发部署不等于真实验收通过，未验证项须随版本留档。性能收敛沿用预先记录的性能阈值；工程稳定性按上节连续两次确认，论文继续改进不无限延长软件优化循环。
